## Resumen ejecutivo

Primera ronda del agente de Implementaciones (no existían informes previos del
Director ni propios). El análisis de producto detectó que Wormy tenía un
**cierre de ciclo incompleto**: el motor generaba informes de auditoría
timestamped (`reports/audit_report_*.json|csv|txt`) pero no existía ninguna
superficie para consumirlos; los perfiles (`stealth`, `aggressive`, `audit`,
`lab_docker`) alteran en silencio parámetros relevantes para la seguridad sin
forma de inspeccionarlos antes de lanzar; y los caps de seguridad solo se
podían cambiar editando YAML.

Se implementaron **3 mejoras completas y funcionales**:

1. **`wormy report`** — hub de lectura de informes post-engagement
   (`list` / `show` / `html`), con salida `--json` y exportación HTML
   autocontenida con escapado XSS.
2. **`wormy config show`** — inspección read-only de la configuración efectiva
   (archivo → perfil → override de targets), con marcadores `[profile]` y
   salida `--json`.
3. **`wormy run --max-infections / --max-runtime`** — overrides por ejecución
   de los caps de seguridad, con validación y aviso prominente al elevarlos en
   modo live.

Resultado: **95 tests nuevos, suite completa 347 pasando / 0 fallos**, black +
isort aplicados, flake8 limpio según los ignores del CI, `compileall` OK y
verificación end-to-end con el motor real (`run --dry-run` → `report list` →
`report show` → `report html`).

## Detalle por mejora

### 1. `wormy report` — hub de informes post-engagement

**Nombre / descripción.** Nuevo subcomando CLI de solo lectura que convierte
la carpeta `reports/` en un historial de engagements consumible:
`wormy report list` (inventario con KPIs), `wormy report show [ID]`
(renderizado en terminal) y `wormy report html [ID]` (exportación HTML
standalone para entregar/compartir).

**Motivación.** El motor escribe 3 ficheros timestamped por engagement, pero
el único modo de consumirlos era abrir el JSON a mano. Para una herramienta
cuya salida final ES el informe de auditoría, la fase de consumo es parte del
producto: un operador necesita comparar engagements, revisar hallazgos y
entregar un documento al responsable del alcance. Además el REPL `report`
regenera un informe nuevo en cada llamada, por lo que el histórico quedaba
disperso e inaccesible.

**Archivos creados/modificados.**
- `worm_core/report_cli.py` (nuevo, ~500 líneas): discovery cronológico de
  informes, resolución de id (timestamp / filename / path / prefijo /
  `latest`), resumen de KPIs, renderizado rich y generador HTML con
  `html.escape` en TODOS los valores dinámicos.
- `worm_core/cli.py`: subparser `report` + epílogo de ejemplos propio
  (`REPORT_EPILOG`) y delegación perezosa.
- `tests/test_report_cli.py` (nuevo): 32 tests.
- `docs/USAGE.md`, `README.md`, `CHANGELOG.md`: documentación.

**Cómo probarla.**
```bash
wormy run --dry-run --target 127.0.0.0/30 --no-monitor   # genera informe real
wormy report list                                        # inventario con KPIs
wormy report show                                        # último, renderizado
wormy report show --json | jq .executive_summary
wormy report html -o entrega.html                        # HTML autocontenido
wormy report list --reports-dir /otro/dir                # directorio alternativo
```
Directorio de informes: `--reports-dir` → `$WORMY_REPORTS_DIR` → `./reports`
→ `<repo root>/reports`. Informes ausentes o corruptos → exit code 1 con
mensaje claro. El comando nunca modifica ni borra informes (auditoría
intocable).

### 2. `wormy config show` — configuración efectiva transparente

**Nombre / descripción.** `wormy config show [--profile P] [--config FILE]
[--target CIDR] [--json]` construye la configuración exactamente como la
construiría el motor para esa invocación y la renderiza por secciones
(Network, Propagation & safety, Evasion & stealth, C2, ML), marcando con
`[profile]` cada valor alterado por el perfil. Muestra a propósito el código
del kill switch (el operador lo necesita para parar el motor).

**Motivación.** Los perfiles cambian en silencio caps de infección, delays,
límite de runtime, stealth y uso de modelos preentrenados. No había forma de
responder "¿qué usará exactamente el motor con `--profile stealth` sobre mi
config.yaml?" sin leer YAML + código fuente y reproducir mentalmente el orden
de overrides. La transparencia ANTES de lanzar es especialmente sensible aquí
porque los valores afectan a la contención (p. ej. `aggressive` sube el cap de
100 infecciones y baja el delay a 0.5s).

**Archivos creados/modificados.**
- `worm_core/config_show.py` (nuevo): comando completo, renderizado y
  `_effective_dict()` para `--json` (incl. bloque `_meta` con el perfil y los
  overrides aplicados).
- `worm_core/config_profiles.py`: nuevo helper compartido
  `apply_profile(config, profile) -> list[str]` que devuelve las claves
  aplicadas como `sección.clave`.
- `worm_core/mixin_base.py`: `_apply_profile()` del motor ahora delega en el
  helper compartido (mismo orden de resolución de secciones:
  propagation → evasion → safety → ml; comportamiento idéntico, pero ahora
  también loguea qué claves aplicó). Esto elimina el riesgo de que el motor y
  la superficie de transparencia diverjan sobre qué significa un perfil.
- `worm_core/cli.py`: subparser `config` + `CONFIG_EPILOG` + export de
  `PROFILE_NAMES`.
- `tests/test_config_show.py` (nuevo): 24 tests (incl. un test de vigilia
  que falla si algún perfil define una clave que ninguna sección acepta).
- `docs/USAGE.md`, `README.md`, `CHANGELOG.md`.

**Cómo probarla.**
```bash
wormy config show                          # config por defecto
wormy config show --profile stealth        # valores con [profile] marcados
wormy config show --profile audit --json   # máquina-legible con _meta
wormy config show --config configs/config_lab.yaml   # valida e inspecciona
wormy config show --target 10.0.0.0/24     # previsualiza override de targets
```
Read-only: no arranca nada, no escribe nada. Fichero de config inválido →
exit 1 con el error de carga.

### 3. `wormy run --max-infections N` / `--max-runtime HOURS`

**Nombre / descripción.** Overrides por ejecución de los caps de seguridad
(`propagation.max_infections` y `safety.max_runtime_hours`) sin editar YAML.
Valores `< 1` → error de uso (exit 2). Elevar un cap por encima de su valor
efectivo en modo live (no dry-run / scan-only) imprime un panel amarillo
"Safety cap raised". En dry-run el override es silencioso (superficie de
simulación).

**Motivación.** Caso de uso diario del lab: "quiero el demo con cap de 2
infecciones" obligaba a tocar `configs/config.yaml` (y recordar revertirlo).
Es el mismo patrón de UX que ya existía para `--target`. El aviso al elevar
caps en live mantiene la filosofía del proyecto: los caps son contención
deliberada, no fricción; si los subes en un engagement real, que quede
registrado y visible.

**Archivos creados/modificados.**
- `worm_core/cli.py`: flags en el parser, `_validate_cap_overrides()` (antes
  de instanciar el motor) y `_apply_cap_overrides()` (después, con logging y
  avisos).
- `tests/test_cli.py`: 14 tests nuevos (clase `TestRunCapOverrides`:
  parsing, validación, aplicación, noop sin flags, aviso solo en live).
- `docs/USAGE.md` (tabla de flags + ejemplo), `README.md` (tabla de comandos
  y tabla de controles de seguridad), `CHANGELOG.md`.

**Cómo probarla.**
```bash
wormy run --dry-run --target 127.0.0.0/30 --max-infections 2   # ok, sin aviso
wormy run --max-infections 0                                    # error de uso
wormy run --max-infections 500 --yes-i-am-authorized            # aviso amarillo
```

## Ideas detectadas pero NO implementadas en esta ronda (backlog)

1. **`wormy report compare <id1> <id2>`**: comparar dos engagements (evolución
   del success rate, duración, infecciones). Natural extensión del hub.
2. **`lab urls` dinámico**: la tabla `LAB_SERVICE_URLS` es estática — no
   refleja el estado real de los contenedores (p. ej. fila del dashboard web
   aunque no haya engine) ni incluye los servicios del compose expandido.
3. **Retención/poda de informes**: `wormy report prune --keep 10` (hoy los
   informes se acumulan indefinidamente; el comando actual es read-only por
   diseño).
4. **REPL `report` integrado con el hub**: `do_report` regenera un informe
   nuevo cada vez; podría ofrecer `report show <id>` sobre el histórico.
5. **`wormy shell --max-infections`**: los flags de caps solo están en `run`;
   el REPL los heredaría bien.
6. **`wormy scan --csv`**: export CSV de resultados de reconocimiento para
   análisis en hoja de cálculo (hoy JSON only).
7. **Enlace desde el dashboard web al último informe HTML** (servir
   `/reports/latest` desde Flask).

## Aspectos detectados que corresponden a otros agentes

**Para Bugs/Seguridad:**
- `utils/audit_report.py::generate()` usa timestamps de **granularidad de
  segundo**: dos generaciones en el mismo segundo (p. ej. REPL `report` +
  informe final automático) colisionan en el mismo nombre de fichero y el
  segundo **sobrescribe** el primero silenciosamente. Recomendación: contador
  de desempate o microseconds.
- `worm_core/mixin_reporting.py`: `reports/final_report.json` y
  `reports/knowledge_graph.json` se sobrescriben en CADA ejecución — el
  grafo/knowledge de engagements anteriores se pierde (los audit_report_*
  sí son timestamped). Deberían llevar timestamp o engancharse al id del
  informe.
- `utils/audit_report.py` línea 3: cabecera "v3.0" y `report_metadata.version
  = "2.0"` mientras el proyecto va por 4.3.1 (metadatos deshonestos en el
  artefacto que entrega el producto).

**Para Pulimiento:**
- README inconsistente sobre el tamaño del lab: Quick start dice "15
  services", la sección Docker lab dice "9 vulnerable services" (`--expanded`
  15). Igual en docs/USAGE.md ("the 15-service variant" vs README).
- `worm_core/cli.py:698`: línea de 106 caracteres (E501 ignorado por CI, pero
  fuera del estándar de 100 del flake8 declarado).
- `LAB_SERVICE_URLS` en `cli.py`: tabla estática con credenciales duplicadas
  frente a lo que ya documenta `docs/USAGE.md` — candidate a data-driven.
- `tests/test_advanced_features.py`: funciones de test que hacen `return`
  booleano en vez de `assert` (PytestReturnNotNoneWarning) — pytest las pasa
  aunque devuelvan False.
