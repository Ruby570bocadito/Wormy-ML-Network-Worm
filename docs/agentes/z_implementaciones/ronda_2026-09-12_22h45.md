## Resumen ejecutivo

Tercera ronda del agente de Implementaciones, centrada en **cerrar el
ciclo de vida del histórico de informes y en llevar el reconocimiento a
la herramienta de hoja de cálculo**. La ronda 2 dejó el hub con list /
show / html / compare, pero el histórico de `reports/` crecía de forma
indefinida sin política de retención; `compare` mostraba siempre los 10
KPIs aunque un script solo quisiera 2-3; y los resultados de `scan` solo
salían en JSON, inútil para analistas que trabajan en Excel/LibreOffice.

Se implementaron **3 mejoras completas y funcionales**:

1. **`wormy report prune [--keep N] [--yes] [--dry-run] [--json]`** —
   política de retención: conserva los N engagements más nuevos (por
   defecto 20) y borra el resto como conjuntos completos
   (`audit_report_<id>.json|csv|txt|html`). Plan siempre previsualizado
   (ids, nº de ficheros, tamaños), confirmación y/N salvo `--yes`,
   `--dry-run` sin tocar nada, `--keep 0` rechazado (borrar toda la
   pista de auditoría nunca está a un flag de distancia), `--json`
   exige `--yes` (los scripts nunca se cuelgan en un prompt).
2. **`report compare --metrics K1,K2`** — filtra la comparación (y su
   JSON) a los KPIs elegidos: coincide por clave máquina (`infected`,
   `success_rate`) o etiqueta humana (`"Success rate"`),
   case-insensitive; nombre desconocido → error de uso listando los
   válidos. También en REPL (`report compare --metrics …`).
3. **`wormy scan --csv FILE`** — export de reconocimiento a CSV: una
   fila por host (ip, hostname, os, open_ports, services,
   vulnerability_score, scan_time); `open_ports`/`services` aplanados
   con `;` (`22:ssh;8080:http`) para que cada host quede en una fila;
   `--csv -` escribe a stdout para piping.

Resultado: **62 tests nuevos, suite completa 443 pasando / 0 fallos**,
black + isort limpios en los ficheros tocados, flake8 sin hallazgos
según los ignores del CI, `compileall` OK y E2E verificado con datos
reales en CLI y REPL (incluido un scan con un puerto 8080 real abierto).

## Detalle de las mejoras

### Mejora 1 — `report prune` (retención del histórico)

**Motivación.** El hub es el consumidor de la pista de auditoría, pero
la pista no tenía fin: cada engagement escribe 3 ficheros y nada los
limpiaba jamás. Backlog de la ronda 2, punto 1.

**Diseño (conservador por principio — es la única operación del hub
que muta algo):**

- `prune_flow(reports_dir, keep, assume_yes, dry_run, as_json, confirm)`
  en `worm_core/report_cli.py`, compartida por CLI y REPL.
-keep=20 por defecto (`PRUNE_DEFAULT_KEEP`); `len(refs) <= keep` →
  "nothing to prune" con exit 0 (también con el directorio vacío).
- El plan se previsualiza siempre (tabla: Report ID / Files / Size) y
  luego: `--dry-run` → mensaje y exit 0 sin tocar nada; sin `--yes` →
  prompt y/N inyectable para tests (`confirm`), EOF/Ctrl-D/"no" →
  aborta con exit 0 (la pista de auditoría es el default seguro).
- Borrado por conjuntos completos: `audit_report_<id>.*` (json, csv,
  txt y el html de export por defecto) vía glob — nunca ficheros
  sueltos ni export con nombre personalizado.
- Errores de borrado se reportan por fichero y la operación termina
  con exit 1 solo si falló algo (intenta todos).
- `--json` (exige `--yes`) emite `{pruned, deleted_files, kept, errors}`;
  `--keep 0/negativo` → exit 2 con mensaje explicativo.

**CLI**: `prune` en choices del action; `--keep N` (default None → 20
en el dispatcher, pero un 0 explícito llega a validación), `--yes/-y`,
`--dry-run`. **REPL**: `report prune [N] [--yes] [--dry-run]` con
`_parse_report_prune_args` (número desnudo o `--keep N`/`-k N`; token
basura → ValueError → error amigable, nunca crash del loop). El docstring
del módulo del hub ahora documenta que `prune` es exactamente la única
operación mutadora.

### Mejora 2 — `compare --metrics`

**Motivación.** Backlog ronda 2, punto 5: scripts que solo quieren 2-3
KPIs tenían que tragarse la tabla de 10 y filtrar en jq.

**Diseño:**

- `compare_metrics` añade `key` a cada fila (campo aditivo, compatible
  con consumidores existentes de `--json`).
- `_filter_metric_rows(rows, "a,b")`: cada nombre casa por clave
  máquina o etiqueta humana (case-insensitive, espacios tolerados);
  devuelve `(picked, unknown)` y el caller convierte unknown no vacío
  en exit 2 listando los válidos (`hosts_discovered (hosts discovered),
  infected (infected), …`).
- `compare_flow(..., metrics=...)` filtra antes de renderizar y de
  serializar; `render_compare` acepta filas prefiltradas.
- CLI: `--metrics K1,K2`; REPL: `-m/--metrics` en
  `_parse_report_compare_args` (ids posicionales + flag).

### Mejora 3 — `wormy scan --csv FILE`

**Motivación.** Backlog ronda 2, punto 3: reconocimiento exportable a
hoja de cálculo.

**Diseño:**

- `_write_scan_csv(results, path)` + `_fmt_services` en
  `worm_core/cli.py` (csv stdlib, `newline=""`, UTF-8).
- Columnas: ip, hostname, os_guess, open_ports, services,
  vulnerability_score, scan_time — cubre ambos scanners (el básico no
  trae hostname/scan_time → celdas vacías; el pro sí).
- `open_ports` → `"22;8080"`; `services` dict → `"22:ssh;8080:http"`
  (claves ordenadas), list → `"smb;rdp"`. Filas no-dict se saltan.
- `path == "-"` → stdout (para piping); 0 hosts → CSV solo-cabecera
  (válido y explícito). `cmd_scan` imprime "CSV written to … (N host(s))".
- Orden = orden del scan (fidelidad, consistente con `--json`).
