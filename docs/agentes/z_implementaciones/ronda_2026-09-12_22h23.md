## Resumen ejecutivo

Segunda ronda del agente de Implementaciones, centrada en **cerrar el ciclo de
análisis de engagements y en la consistencia entre superficies**. El hub de
informes (ronda 1) permitía listar y leer engagements, pero no compararlos; el
REPL `report` seguía regenerando un informe nuevo cada vez sin acceso al
histórico; y los flags de caps de seguridad (`--max-infections` /
`--max-runtime`) solo existían en `wormy run`, obligando a editar YAML para una
sesión de REPL con cap ajustado.

Se implementaron **3 mejoras completas y funcionales** (más dos correcciones
menores detectadas durante el trabajo):

1. **`wormy report compare [ID1] [ID2]`** — comparación lado a lado de dos
   engagements con deltas firmados sobre 10 KPIs, flechas de tendencia
   (▲ mejor / ▼ peor / delta plano = neutral) y salida `--json`.
2. **REPL `report` integrado con el hub** — `report list | show | compare |
   html` dentro del shell interactivo (read-only), con `report` / `report new`
   manteniendo el comportamiento anterior (generar informe de la sesión).
3. **`wormy shell --max-infections / --max-runtime`** — el REPL hereda los
   flags de caps de `run`: validación fail-fast antes de arrancar el motor
   (exit 2), aplicación con logging y aviso "Safety cap raised" al elevar en
   modo live.

Correcciones menores incluidas: la tabla `help` del REPL ahora escapa el
markup de rich (los hints de uso `run [n]`, `scan [pro|basic]` se estaban
tragando silenciosamente), y `_apply_cap_overrides` tolera namespaces sin
`scan_only` (bug latente al reutilizarla desde `shell`).

Resultado: **62 tests nuevos, suite completa 410 pasando / 0 fallos**, black +
isort limpios, flake8 sin hallazgos según los ignores del CI, `compileall` OK
y E2E verificado con motor real en CLI y REPL.

## Detalle por mejora

### 1. `wormy report compare [ID1] [ID2]` — análisis comparativo de engagements

**Nombre / descripción.** Nueva acción del hub de informes que responde a la
pregunta natural post-engagement: "¿mejoró respecto al anterior?". Renderiza
una tabla con 10 KPIs (hosts descubiertos, infectados, fallidos, success
rate, duración, scans, vulnerabilidades, credenciales, movimientos laterales,
recomendaciones) con el valor baseline, el valor candidate, y el delta firmado
con color/flecha según si el cambio es mejor (verde ▲), peor (rojo ▼) o neutral.

**Semántica de resolución** (el informe más reciente es siempre el candidato):

- `report compare` → últimos dos engagements
- `report compare A` → A contra su predecesor inmediato
- `report compare A B` → ambos resueltos; el más antiguo es baseline
  (cualquier orden aceptado, se ordena cronológicamente)

Errores claros con exit 1: id desconocido, comparar un informe consigo mismo,
el informe más antiguo sin predecesor (sugiere pasar dos ids), informe
corrupto, o menos de dos engagements en el directorio.

**Decisiones de diseño.**

- Direcciones de "mejor" explícitas por métrica: infectados/éxito/cobertura
  arriba = mejor; fallidos arriba = peor; duración/scans/recomendaciones
  neutrales (sin juicio de valor documentado en el pie de la tabla).
- La duración se parsea desde el formato real del motor
  (`str(timedelta)`: "0:00:02.044012", "1 day, 0:00:02", "N/A") a segundos
  para poder calcular delta; si alguna no parsea, la fila degrada a neutral
  sin delta en lugar de fallar.
- `--json` emite `{baseline: {id, path}, candidate: {id, path}, metrics:
  [{metric, baseline, candidate, delta, trend}]}` — diferencias y tendencia
  listas para consumir por scripts/CI.

**Archivos creados/modificados.**
- `worm_core/report_cli.py`: `_parse_duration()`, `_parse_rate()`, tabla
  declarativa `_METRICS`, `compare_metrics()` (modelo), `render_compare()`
  (render), `_resolve_ref()`/`_ref_index()`, `compare_flow()` (resolución +
  flujo completo reutilizable), refactor de `show_report()`/`export_html()`
  como flujos compartidos CLI/REPL, dispatch de `compare` en `cmd_report()`.
- `worm_core/cli.py`: acción `compare` en el parser, segundo id posicional
  (`ID1`/`ID2` con metavars), `REPORT_EPILOG` ampliado.
- `tests/test_report_cli.py`: +29 tests (parsing de duración/rate, modelo de
  métricas con tendencias, flujo completo con casos límite, JSON, cmd_report).
- `docs/USAGE.md`, `README.md`, `CHANGELOG.md`.

**Cómo probarla.**
```bash
wormy run --dry-run --target 127.0.0.0/30 --no-monitor   # nuevo engagement
wormy report compare                                    # últimos dos
wormy report compare 20260912_215239                    # vs. su predecesor
wormy report compare 20260912_215018 20260912_215239    # par explícito
wormy report compare --json | jq '.metrics[] | select(.metric=="Infected")'
```

### 2. REPL `report` integrado con el hub de informes

**Nombre / descripción.** El comando `report` del shell interactivo pasa de
"regenera un informe cada vez" a operar también sobre el histórico (read-only):

```
report                      # informe de la sesión actual (compat. total)
report new                  # ídem, explícito
report list                 # inventario de engagements pasados
report show [id]            # render de un informe histórico
report compare [id1 id2]    # deltas baseline → candidate
report html [id] [-o FILE]  # export HTML autocontenido
```

**Motivación.** El REPL es la superficie de trabajo durante el engagement;
el hub (ronda 1) solo existía en la CLI post-engagement. Un operador que
termina la sesión tenía que salir del shell para revisar el histórico o
entregar un HTML. Ahora el ciclo completo (ejecutar → generar → consultar
historial → comparar → exportar) vive en ambas superficies.

**Decisiones de diseño.**

- **Cero duplicación**: el REPL delega en las mismas funciones públicas del
  hub (`render_list`, `show_report`, `compare_flow`, `export_html`), que la
  CLI también usa tras el refactor — comportamiento idéntico garantizado por
  construcción, no por disciplina.
- **Contención de errores**: cualquier fallo del hub dentro del REPL se
  imprime como error y jamás rompe el bucle `cmd.Cmd` (try/except con
  mensaje; test dedicado que fuerza un `RuntimeError`).
- `report html -o` sin ruta o con dos ids → error de uso legible (viajero
  por la misma excepción capturada).
- La tabla `help` del REPL documenta la nueva sintaxis.

**Fix incluido (detectado al testear):** rich interpretaba los corchetes de
los hints de uso como tags de markup y los eliminaba silenciosamente — la
fila de ayuda mostraba `run` en vez de `run [n]`, `scan` en vez de
`scan [pro|basic]`. Ahora las celdas pasan por `rich.markup.escape()`
(preexistente en todas las filas, no solo en la mía).

**Archivos creados/modificados.**
- `worm_core/shell.py`: `do_report` reescrito (dispatch de subcomandos con
  import perezoso del hub), `_parse_report_html_args()` (parser de tokens
  `html [id] [-o FILE]`), fila de `do_help` actualizada, `escape` en la
  tabla de ayuda.
- `tests/test_shell_report.py` (nuevo, 22 tests): compatibilidad hacia
  atrás, dispatch de cada subcomando sobre informes reales, parsing de
  `html` (7 casos), contención de errores (2), entrada de ayuda. Usa un
  worm falso + informes reales del generador.
- `docs/USAGE.md` (tabla REPL + walkthrough), `README.md`, `CHANGELOG.md`.

**Cómo probarla.**
```bash
wormy shell --dry-run
> report list
> report show
> report compare
> report html -o entrega.html
> report          # informe de esta sesión
```

### 3. `wormy shell --max-infections N / --max-runtime HOURS`

**Nombre / descripción.** Los flags de caps por ejecución de `wormy run`
(ronda 1) se extienden a `wormy shell`: misma validación (>=1, exit 2 con
mensaje), misma aplicación (logging del valor antiguo → nuevo) y mismo aviso
amarillo "Safety cap raised" al ELEVAR un cap en modo live (sin `--dry-run`).

**Motivación.** Caso de uso diario del lab: "demo interactiva con cap de 2
infecciones" obligaba a editar `configs/config.yaml` (y acordarse de
revertirlo) porque el REPL no aceptaba los flags que ya existían en `run`.
Paridad de superficie: la contención deliberada debe ser configurable igual
de fácil en ambos puntos de entrada.

**Detalles de implementación.**
- Validación fail-fast **antes** de instanciar `WormCore` (mismo contrato
  que `cmd_run`; el test de wiring verifica que un valor inválido aborta
  sin arrancar el motor).
- `_apply_cap_overrides()` ahora usa `getattr(args, "scan_only", False)`:
  los namespaces de `shell` no llevan `scan_only` y la función reventaría
  con `AttributeError` al evaluar el guard del aviso (bug latente, cubierto
  por test de regresión).
- Aplicación tras el override de targets, antes de entrar al cmdloop; el
  `finally: worm.shutdown()` existente garantiza limpieza.

**Archivos creados/modificados.**
- `worm_core/cli.py`: flags en el subparser `shell`, validación y aplicación
  en `cmd_shell()`, fix `getattr` en `_apply_cap_overrides()`.
- `tests/test_cli.py`: +11 tests (parsing, defaults, flags comunes
  conservados, validación con namespace sin `scan_only`, wiring completo
  con WormCore/InteractiveCLI mockeados, rechazo fail-fast).
- `docs/USAGE.md` (sección shell), `README.md` (tabla de comandos + quick
  start), `CHANGELOG.md`.

**Cómo probarla.**
```bash
wormy shell --dry-run --max-infections 2        # demo con cap ajustado
wormy shell --max-infections 0                  # error de uso, exit 2
wormy shell --max-infections 500                # aviso "Safety cap raised" (live)
```
