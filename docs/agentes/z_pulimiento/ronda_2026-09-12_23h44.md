## Detalle por cambio

### 1. Unificación del ciclo de vida: `shutdown()` → `stop()` en el web dashboard

- **Qué y por qué**: el lanzador standalone (`python -m monitoring.web_dashboard`) llamaba a `dash.shutdown()` en el handler de `KeyboardInterrupt`, pero la clase `WebDashboard` **no tiene ningún método `shutdown()`** — el método real es `stop()` (consistente con `ArmitageDashboard`). Al pulsar Ctrl+C en modo standalone se producía un `AttributeError` justo en la ruta de salida. Se unifica la nomenclatura del ciclo de vida y se alinean los comentarios internos que referenciaban el nombre antiguo. Aprovecho para mover el `import json` de dentro de `_safe_str()` al nivel de módulo (import perezoso innecesario: Flask ya depende de json).
- **Archivos modificados**: `monitoring/web_dashboard.py`
- **Impacto esperado**: mantenibilidad y consistencia de la API interna de los tres dashboards (`run` / `stop` / `run_background`); salida limpia por Ctrl+C en modo standalone; legibilidad.

### 2. Eliminación de polling duplicado de `/api/hosts` en el dashboard web

- **Qué y por qué**: el frontend del dashboard ejecutaba **dos intervals de 5 s independientes** — uno con `refreshAll()` (que ya llama a `loadHosts()`) y otro dedicado exclusivamente a `jget('/api/hosts')` para alimentar `window._hostsCache` (caché usada por el diálogo de drill-down de hosts). Además, en `window.onload` se hacía una petición extra de la misma URL. Resultado: **el mismo endpoint se solicitaba el doble de veces de lo necesario** (2 peticiones/5 s + 1 extra en carga). Ahora la caché se actualiza dentro del propio `loadHosts()` y se eliminan el interval y el fetch redundantes.
- **Archivos modificados**: `monitoring/web_dashboard.py` (JS embebido)
- **Impacto esperado**: rendimiento (mitad de peticiones HTTP al backend desde el navegador), menos contención con los otros 4 endpoints que ya se polling cada 5 s, y menos código duplicado con una única fuente de verdad para la caché de hosts.

### 3. Código muerto y re-silenciado redundante en el Armitage dashboard

- **Qué y por qué**: (a) en el renderizado del mapa canvas existía una variable local `const color = host.status === 'infected' ? 'var(--success)' : ...` que se asignaba y **nunca se usaba** (el color real se calcula en `nodeColor`); además sus valores eran cadenas CSS `var(--...)` que ni siquiera funcionarían en un contexto canvas 2D — código muerto doblemente confuso. (b) dentro de `run()` se repetía el silenciado del logger de werkzeug (`import logging as _log` + `setLevel(ERROR)`) que **ya se hace a nivel de módulo** (línea 23); el import local y la re-configuración eran redundantes.
- **Archivos modificados**: `monitoring/armitage_dashboard.py`
- **Impacto esperado**: legibilidad del bloque de renderizado (se elimina una variable que invitaba a confusión con `nodeColor`), y arranque del dashboard más limpio sin import/config duplicados.

### 4. Re-silenciado redundante de logs en el credential dashboard

- **Qué y por qué**: mismo patrón que el punto 3(b): `run()` repetía `import logging as _log` + silenciado de werkzeug que ya está hecho a nivel de módulo (líneas 17-18). Se elimina la duplicación para que quede un único punto de configuración de logs por módulo, igual que en `web_dashboard.py` y `cli_monitor.py`.
- **Archivos modificados**: `monitoring/credential_dashboard.py`
- **Impacto esperado**: consistencia estructural entre los cuatro módulos con servidores HTTP del paquete `monitoring/`; eliminación de código duplicado.

### 5. Refactor del hack de pseudo-namespace en `wormy lab up`

- **Qué y por qué**: `cmd_lab()` recursaba sobre sí misma fabricando un objeto argparse falso con `cmd_lab(type("A", (), {"action": "urls", "expanded": expanded})())` para imprimir el cheat-sheet de servicios tras levantar el lab. Es un patrón oscuro (clase dinámica con atributos inyectados para simular `args`) que confunde la lectura y el tipado. Se extrae `_print_lab_urls()` como helper explícito y `cmd_lab` lo invoca directamente; el código de la tabla de URLs pasa a vivir junto al resto de helpers del módulo lab.
- **Archivos modificados**: `worm_core/cli.py`
- **Impacto esperado**: legibilidad y mantenibilidad del subcomando `lab` (comportamiento idéntico: misma tabla, mismo exit code, verificado con tests y smoke manual).
